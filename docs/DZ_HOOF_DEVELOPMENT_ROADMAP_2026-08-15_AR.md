## 3. الخارطة المقترحة للمرحلة التالية

### المرحلة A — قبول Android TV فعليًا

هذه هي الخطوة الأولى قبل إضافة ميزات كبيرة جديدة. يجب تشغيل workflow Android في GitHub أو بيئة Android Studio والتحقق من `lintDebug` و`testDebugUnitTest` و`assembleDebug`. بعد ذلك يُختبر APK على Android TV أو Fire TV بمصدر M3U/Xtream مصرح به: pairing عبر PIN وQR، تحميل القنوات، تشغيل القناة، تبديل القنوات، المفضلة، EPG، fallback، QoE، واستعادة التركيز بعد الرجوع من المشغل.

**معيار الخروج:** APK Debug قابل للتثبيت، لا أخطاء Kotlin/Gradle، ونتيجة اختبار تشغيل موثقة على Emulator أو جهاز فعلي.

### المرحلة B — مراجعة انتقائية لـT1 والإنتاج

بعد قبول Android، تتم مراجعة PR #30 على شكل وحدات مستقلة: activation gate، ربط الاشتراك بخطة المشاهدة، content access، تقوية أسرار الإنتاج، MongoDB/Redis authenticated compose، وRelease signing. لا تُنقل أي وحدة قبل كتابة اختبار Backend أو Android مناسب لها ومقارنة عقد API الحالي.

**معيار الخروج:** تدفق اشتراك واضح لا يكشف مصادر البث، اختبارات صلاحية الخطة ناجحة، وDocker/production configuration قابلة للتحقق دون أسرار داخل Git.

### المرحلة C — قيادة جودة Live TV

بعد تثبيت التشغيل، تُستعمل بيانات QoE وhealth score لتحسين ترتيب القنوات، رسائل الانقطاع، fallback recommendation، ومؤشرات لوحة الإدارة. ثم يرفع EPG إلى تجربة Now/Next غنية بالصور مع إصلاح unmatched channels ومؤشرات coverage لكل مصدر.

**معيار الخروج:** انخفاض زمن بدء التشغيل وإعادة التقطيع وفق telemetry، تحسن coverage، ومسار واضح للمشرف لمعالجة القنوات غير المطابقة.

### المرحلة D — مزايا الاحتفاظ بالمستخدم

تُضاف Continue Watching وسجل المشاهدة، اختيار الصوت والترجمة عند توفرهما، وتحسين البحث والـPoster. يؤجل DVR/timeshift إلى ما بعد استقرار الأساس، لأن التسجيل وإدارة التخزين يضيفان مخاطر تشغيلية لا ينبغي إدخالها قبل ثبات Live TV وEPG وQoE.

**معيار الخروج:** استئناف مشاهدة موثوق، حفظ آمن وغير حساس، وتجربة ريموت متماسكة على TV.

### المرحلة E — جاهزية النشر العام

تُنفذ مراجعة domain/HTTPS، نسخ MongoDB وRedis الاحتياطية، restore drill، مراقبة الأخطاء، rate limiting، وإطلاق Pilot محدود قبل النشر العام. تُراجع جميع مصادر القنوات لتأكيد التفويض القانوني وتبقى أسرار التشغيل خارج المستودع.

**معيار الخروج:** نشر قابل للاسترجاع والمراقبة، مع خطة rollback ونسخ احتياطية مجربة.

## 4. ما يجب أن يفعله المستخدم لتحديد الخطوة التالية

القرار المطلوب الآن هو اختيار أحد مسارين. المسار الموصى به هو **المسار 1: قبول Android TV فعليًا أولًا**؛ يحتاج المستخدم إلى تشغيل GitHub Actions أو تزويد بيئة Android Studio/Emulator، ثم اختبار pairing والتشغيل بمصدر مصرح. المسار البديل هو **المسار 2: مراجعة PR #30 انتقائيًا** إذا كان الهدف العاجل هو الاشتراكات وproduction hardening بدل اختبار الجهاز.

لا أوصي بدمج PR #28 أو #29 أو #30 دفعة واحدة، لأن `main` الحالي يحتوي بالفعل على نسخ أحدث من أجزاء Android وCI وplayback. الاختيار الآمن هو استخراج ما يوافق قرار المنتج، اختباره، ثم دمجه في PRs صغيرة قابلة للرجوع.

## 5. القرار التنفيذي المقترح

ابدأ بالمسار 1: **Android TV Acceptance Gate**. بعد نجاحه، نفذ وحدة activation/subscription من PR #30 فقط إن كانت مطلوبة تجاريًا، ثم انتقل إلى تحسين QoE وEPG قبل DVR/timeshift. بهذه الأولوية يبقى DZ HOOF منافسًا في Live TV دون تضخيم نطاق المنتج أو المخاطرة باستقرار التشغيل.
