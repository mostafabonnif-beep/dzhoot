# تقرير التحقيق التقني في مصدر Xtream

## الخلاصة التنفيذية

تمت مراجعة مصدر Xtream الذي قدمه المستخدم واختباره مباشرة من بيئة DZ HOOF. الحساب **ينجح في المصادقة** ويعيد بيانات القنوات، لكنه لا يعيد أي bytes عند طلب بث قناة فعلية. لذلك توجد مشكلة حقيقية في طبقة Live Playback أو في سياسة الحساب/عنوان الوصول، وليست مشكلة في شاشة تطبيق العميل أو كود التفعيل.

يوجد حل برمجي داخل DZ HOOF فقط عندما يسمح المزود بالبث من عنوان Backend أو عندما يعمل رابط قناة فعلي يمكن للخادم تمريره بأمان. أما عندما تعيد كل مسارات التشغيل 456 أو 513 أو 403 مع حجم صفر، فلا يستطيع Backend إنشاء البث من metadata وحدها.

## الأدلة الفعلية من الحساب

| الاختبار | النتيجة |
|---|---|
| `player_api.php` | HTTP 200 |
| `user_info.auth` | `1` |
| حالة الحساب | `Active` |
| الاتصالات الحالية | `0` |
| الحد الأقصى للاتصالات | `1` |
| صيغ الإخراج المسموح بها في metadata | `m3u8`, `ts`, `rtmp` |
| `get_live_streams` | 16,609 قناة |
| `stream_id` المختبر | `262849` |
| `direct_source` للقناة | فارغ |

## مسارات التشغيل التي اختُبرت

رابط التشغيل القياسي المبني من `stream_id` هو `/live/username/password/stream_id.ts`، وهو متوافق مع توثيق Xtream المفتوح المصدر [1]. جُرّبت هذه الصيغة وصيغها القياسية الأخرى على العنوانين اللذين قدمهما المستخدم.

| المسار أو الإخراج | النتيجة العملية |
|---|---|
| `/live/.../262849.ts` | HTTP 456، حجم صفر |
| `/live/.../262849.m3u8` | HTTP 456، حجم صفر |
| `/live/.../262849` | HTTP 513، حجم صفر |
| `/stream/.../262849.ts` | HTTP 513، حجم صفر |
| `/hls/.../262849.m3u8` | HTTP 403، حجم صفر |
| `get.php` مع `output=ts` | HTTP 884، حجم صفر |
| `get.php` مع `output=m3u8` | HTTP 884، حجم صفر |
| `get.php` مع `output=hls` | HTTP 884، حجم صفر |

## التفسير التقني

النجاح في `player_api.php` يثبت أن اسم المستخدم وكلمة المرور والعنوان صالحون للوصول إلى API. لكنه لا يثبت أن الحساب يسمح بتشغيل الفيديو من كل عنوان IP أو أن طبقة البث مفعلة. وجود `max_connections=1` يجعل حد الاتصال عاملًا مهمًا، كما أن توثيق أنماط Xtream المجتمعي يذكر قيود IP whitelist وUA whitelist وGeoIP وISP Lock وFlood Protection [2].

HTTP 456 ظهر مباشرة من مسار live وبحجم صفر، وهو متوافق مع تفسير مزودي/مشغلات IPTV له كرفض للحصة أو الاتصال أو صلاحية البث. في مثال دعم Emby، انتهت حالة مماثلة بإعطاء المزود عنوانًا جديدًا يعمل [3]. أما HTTP 884 فظهر من مسار M3U فقط، وتوجد تقارير مجتمعية تربطه بقائمة M3U مقفلة أو مرفوضة [4]. هذه التقارير المجتمعية ليست مواصفة رسمية، ولذلك لا ينبغي اعتبارها تفسيرًا قطعيًا منفردًا.

## الحلول البرمجية المشروعة

الحل الأول هو أن يخزن DZ HOOF بيانات Xtream في Backend فقط، ثم يستعمل `player_api.php` لمزامنة metadata ويبني رابط التشغيل القياسي عند طلب قناة. هذا الجزء مدعوم في تصميم المشروع، لكنه لن ينجح إلا بعد أن يعيد مزود Xtream بيانات البث من مسار live.

الحل الثاني هو تشغيل Backend على VPS ذي عنوان IP ثابت، ثم يطلب المزود إضافة عنوان VPS إلى IP whitelist إذا كان الحساب مقيدًا بعنوان معين. هذا حل شبكي مشروع وليس تجاوزًا؛ يحتاج موافقة المزود. لا يمكن إثباته من sandbox وحده لأن عنوان الخروج المسموح لدى المزود غير معروف.

الحل الثالث هو طلب حساب جديد أو رابط Portal/M3U جديد يملك Live Playback. الأفضل أن يعطي المزود قناة اختبار واحدة، ثم تُختبر في VLC أو curl من نفس بيئة VPS قبل إدخالها إلى التطبيق.

الحل الرابع، إذا كان البث يعمل في تطبيق رسمي لدى المزود لكنه يفشل في Backend، هو أن يراجع المزود User-Agent أو Referrer أو سياسة server-to-server. لا ينبغي تقليد تطبيق مغلق أو تجاوز حماية الحساب؛ المطلوب أن يسمح المزود صراحةً بخادم DZ HOOF.

## ما لا يمكن إصلاحه من داخل التطبيق

لا يمكن تحويل قائمة أسماء القنوات إلى فيديو عندما لا يرسل المزود bytes من endpoint البث. كما لا يمكن أن يصلح proxy أو ExoPlayer حالة يكون فيها المصدر نفسه يعيد 456/513/403. وضع هذه القنوات في APK سيجعلها تظهر للعميل ثم تفشل عند التشغيل، وهذا أسوأ من إخفائها أو تعليمها غير متاحة.

## خطة الحسم

اطلب من المزود تنفيذ ثلاث نقاط: تفعيل Live Playback للحساب، زيادة الحد إلى اتصالين مؤقتًا للاختبار أو التأكد من تحرير الاتصال السابق، وإضافة عنوان VPS إلى IP whitelist إن كانت مفعلة. بعد ذلك اطلب رابط قناة اختبار واحدة. إذا أعاد الرابط HTTP 200 مع `Content-Type` بث أو ملف HLS صالح، نربط المصدر في Backend ونختبره من خلال تطبيق العميل. إذا استمر HTTP 456 من عنوان VPS، فالحساب غير صالح للبث مهما كانت metadata ظاهرة.

## اختبارات إضافية بعد البحث

تم اختبار `https://tv.upstream-host-redacted` بوصفه Portal بديلًا. هذا العنوان يعيد `player_api` بنجاح، بينما عنوان `cf` لم يكن ثابتًا في اختبار Portal الأخير. رغم ذلك، أعادت صيغ التشغيل من عنوان `tv` نفس HTTP 456، وأعاد M3U HTTP 884.

تم اختبار ست قنوات من مواضع مختلفة في قائمة 16,609 قناة، بينها قنوات من فرنسا وباكستان والولايات المتحدة والعربية، وكانت جميعها تعيد HTTP 456 وحجم صفر. هذا يستبعد أن تكون المشكلة محصورة في القناة الأولى.

النتيجة الجديدة: العنوان الأنسب لاختبار API هو `tv.upstream-host-redacted`، لكن طبقة البث نفسها ترفض جميع القنوات المختبرة. الحلول الإضافية الواقعية تنحصر في طلب إزالة IP/UA/connection restriction أو إصدار Portal/حساب جديد، ثم إعادة الاختبار من VPS ثابت.
