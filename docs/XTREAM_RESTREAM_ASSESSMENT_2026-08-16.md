# تقييم إعادة بث مصادر Xtream إلى DZ HOOF

**التاريخ:** 16 أغسطس 2026

## الخلاصة التنفيذية

تم فحص الرابطين اللذين قدمهما المستخدم بصورة سلبية ومحدودة، ومقارنة النتيجة مع اختبارات DZ HOOF السابقة. النتيجة الحاسمة هي أن المشكلة ليست في كود التفعيل أو تطبيق Android أو HLS proxy داخل المشروع. المصدر يرفض طبقة التشغيل نفسها، ولذلك لا يمكن لأي تعديل داخل التطبيق إنشاء فيديو من قائمة القنوات أو من metadata فقط.

> **القرار التقني:** لا يمكن اعتماد هذين الرابطين للإطلاق قبل أن يسمح المزود صراحةً بالبث من خادم DZ HOOF أو يصدر حساباً/Portal مخصصاً لإعادة التوزيع.

> **القرار القانوني:** أنا لست محامياً؛ هذا تحليل عملي وليس استشارة قانونية رسمية. يجب مراجعة محامٍ جزائري قبل توقيع عقد أو إطلاق خدمة مدفوعة.

## نتيجة الفحص الحالي

| المصدر | الاختبار | النتيجة |
|---|---|---|
| `cf.upstream-host-redacted` | طلب M3U من الرابط المقدم | HTTP 401 مع رد `Off-limits` وحجم صغير، أي أن نقطة التصدير مرفوضة حالياً من المزود. |
| `tv.upstream-host-redacted` | طلب M3U من الرابط المقدم | HTTP 884 دون بيانات بث. |
| `player_api.php` في الاختبارات السابقة | API metadata | نجح في المصادقة وإرجاع بيانات القنوات في بعض الاختبارات. |
| مسارات Live السابقة | تشغيل قنوات فعلية | HTTP 456/513/403 مع حجم صفر عبر قنوات متعددة. |

الفرق بين نجاح API وفشل البث مهم: المصادقة تثبت أن الحساب يستطيع قراءة بعض بيانات اللوحة، لكنها لا تثبت أن الحساب يسمح بالتشغيل من عنوان IP الخاص بـ Backend أو بإعادة البث إلى عملاء آخرين. يوضح التقرير الداخلي السابق مسارات التشغيل التي اختبرت، وحد الاتصال الأقصى، واستنتاجات IP/UA/connection restriction [4].

## لماذا لا يصلح Proxy أو FFmpeg كحل لهذه الحالة؟

الـ proxy يستطيع تمرير bytes موجودة أصلاً، وFFmpeg يستطيع تحويل أو إعادة تغليف بث قابل للقراءة. عندما يعيد المصدر 456 أو 403 أو 884 مع حجم صفر، لا توجد إشارة فيديو ليقوم الخادم بتمريرها أو تحويلها. محاولة تغيير User-Agent عشوائياً أو تقليد تطبيق مغلق أو البحث عن endpoint بديل بهدف تجاوز المنع ليست حلاً مدعوماً، وقد تخالف شروط المزود أو حقوق أصحاب المحتوى.

## ما الذي يجب طلبه من المزود؟

الحل العملي الأول هو طلب **حساب B2B/Reseller مخصص لإعادة التوزيع**، وليس اشتراك مشاهدة عادي. يجب أن يذكر المزود كتابةً أن الحساب يسمح بإعادة البث إلى تطبيق DZ HOOF، وأن يحدد الدول المسموح بها، وعدد العملاء أو الاتصالات، وصيغ التسليم، وحقوق EPG والشعارات، وسياسة DRM أو token، ومدة الترخيص ومستوى الخدمة.

الحل الثاني هو تشغيل Backend على VPS بعنوان IP ثابت، ثم طلب إضافة عنوان الخادم إلى IP whitelist إذا كانت طبقة البث مقيدة بمصدر اتصال محدد. هذا ليس تجاوزاً؛ هو إعداد يفعله المزود بموافقته. لا يمكن إثبات نجاحه من Sandbox لأن عنوان الخروج ليس عنواناً ثابتاً مناسباً للإنتاج.

الحل الثالث هو طلب قناة اختبار واحدة تعمل من نفس VPS قبل إدخال أي مصدر إلى الكتالوج. الاختبار المطلوب هو أن يعيد رابط القناة فعلياً HTTP 200 مع manifest HLS صالح أو stream bytes صالح، ثم ينجح فحص manifest وchild playlist وsegment من Backend نفسه.

الحل الرابع هو أن يزوّدنا المزود بتوثيق رسمي لأي متطلبات توافق، مثل `User-Agent` أو `Referer` أو headers خاصة أو endpoint server-to-server. يمكن حينها إضافة هذه الإعدادات إلى تكامل DZ HOOF بطريقة موثقة ومحدودة. لا ينبغي تخمين هذه القيم أو استعمالها لتجاوز حماية الحساب.

## التغييرات الآمنة التي يدعمها المشروع

المشروع يحتوي بالفعل على أهم طبقات التسليم الآمن: تخزين الاعتمادات في Backend، عدم إرسال بيانات Xtream إلى تطبيق العميل، التحقق من API وM3U وLive Playback منفصلة، حجب المصادر غير المتحققة، إنشاء playback tokens قصيرة العمر، وتمرير HLS عبر نطاق المشروع.

يمكن إضافة تحسينات تشغيلية بعد الحصول على حساب مصرح، منها حقل يثبت حالة الترخيص ونطاقه، وتسجيل عنوان VPS المصرح به، ودعم headers موثقة لكل مصدر، واختبار قناة مرجعية عند إضافة المصدر، وتقرير واضح يفرق بين `api-authenticated` و`m3u-blocked` و`live-playback-blocked` و`provider-ip-not-whitelisted`. هذه التحسينات تزيد الوضوح ولا تفتح المصدر غير المصرح به للعملاء.

أما إضعاف شرط `verificationStatus=verified` أو السماح بالمزامنة اعتماداً على نجاح API فقط فسيكون تراجعاً خطيراً، لأنه سيجعل القنوات تظهر للزبون ثم تفشل عند التشغيل. لذلك لن يتم تطبيق هذا النوع من التغيير.

## التحقق القانوني المطلوب

يحمي قانون الجزائر رقم 03-05 حقوق المؤلف والحقوق المجاورة، ويشمل حماية الأعمال السمعية البصرية وحقوق مؤسسات البث [1]. وتنص المادة 27، بحسب النص المنشور في WIPO Lex، على حقوق حصرية تشمل نقل العمل إلى الجمهور بالبث السمعي أو السمعي البصري، ونقل العمل المبثوث إلى الجمهور عبر الأسلاك أو أي وسيط لنقل الإشارات، وكذلك نقله عبر نظام لمعالجة المعلومات [1]. كما تذكر المواد 30 و31 صوراً من البث وإعادة التوزيع المرتبطة بترخيص ومقابل عادل [1].

توضح ONDA رسمياً أنها مؤسسة عمومية تحت وصاية وزارة الثقافة والفنون، ومهمتها حماية الحقوق المعنوية والمادية للمؤلفين وأصحاب الحقوق المجاورة وإدارة الحقوق جماعياً [2]. لذلك يجب توثيق سلسلة الحقوق مع المزود أو مالك القناة، ولا يكفي شراء بيانات دخول Xtream بحد ذاته.

ومن الناحية التقنية، يوضح دليل Flussonic لخدمات IPTV أن الخدمات المدفوعة أو المرخصة تحتاج إلى حماية للمحتوى، مثل DRM أو token authentication، وأن إطلاق الخدمة يتطلب حقوقاً من المذيعين أو aggregators والامتثال للقوانين المحلية [3].

## رسالة جاهزة للمزود

يمكن إرسال النص التالي للمزود:

> نريد تشغيل حساب B2B/Reseller قانوني لتوزيع القنوات داخل تطبيق DZ HOOF. نرجو تأكيد أن الحساب يسمح server-to-server restreaming إلى خادمنا، وتزويدنا بمتطلبات IP whitelist أو User-Agent/headers الرسمية، والحد الأقصى للاتصالات، وصيغ HLS/TS المدعومة، وEPG، والدول المسموح بها، وSLA، ووثيقة تثبت حق إعادة التوزيع. سنرسل عنوان IP ثابتاً لـ VPS بعد الحصول عليه. نحتاج أيضاً إلى رابط قناة اختبار واحدة تعمل من عنوان الخادم نفسه قبل تفعيل أي قناة للعملاء.

## القرار النهائي

لن أضيف داخل DZ HOOF أي كود هدفه تجاوز `401 Off-limits` أو `456` أو `884` أو تقليد تطبيق المزود أو التحايل على IP/UA/connection restriction. التغيير الصحيح هو الحصول على إذن المزود وحساب B2B أو مصدر مرخص، ثم تزويدي بعنوان VPS الثابت ورابط قناة اختبار واحدة. عندها يمكن ربط المصدر في Backend، تشغيل diagnostics، التحقق من HLS، ثم بناء APK الإنتاجي دون إعادة تثبيت المشروع.

## تحديث تنفيذي بعد إعادة الفحص

تمت إعادة فحص الحساب من المسارات القياسية الرسمية. أعاد `player_api.php` حالة HTTP 200 وقائمة `get_live_streams` تضم 16,609 عنصراً، بينما أعاد M3U HTTP 884 دون bytes. واختُبرت ثلاث قنوات من العينة عبر `/live/{user}/{pass}/{stream_id}.m3u8` و`.ts`؛ أعادت الصيغتان HTTP 456 وحجم صفر لكل القنوات المختبرة.

أُضيف إلى Backend تحسين توافق آمن: أثناء diagnostics يجرب النظام الصيغة القياسية `m3u8` ثم `ts` فقط، ويحفظ `playbackFormat` الذي نجح فعلياً، ثم يستخدمه عند إنشاء روابط القنوات وعند preview/sync. أُضيف اختبار regression يثبت أن مصدراً يعمل بصيغة TS فقط يُقبل ويحصل على روابط `.ts`. هذا التغيير لا يفتح مصدراً metadata-only ولا يتجاوز 401/456/884؛ وبالنسبة للحساب الحالي تبقى النتيجة `blocked/degraded` إلى أن يفعّل المزود Live Playback.
