# دليل النطاق الثابت والتنقل بين VPS — DZ HOOF IPTV

## الإجابة المختصرة

نعم، يمكنك إعطائي **النطاق الثابت** عند الحصول عليه. النطاق لا يكون داخل VPS؛ هو مملوك لدى شركة تسجيل النطاق أو مزود DNS، ونقوم فقط بتوجيهه إلى عنوان IP الخاص بالخادم الحالي. عند الانتقال لاحقًا من Oracle إلى AWS أو أي VPS آخر، لا نعيد إنتاج التطبيق إذا حافظنا على النطاق نفسه وعقد API نفسه. نغيّر سجل DNS من IP الخادم القديم إلى IP الخادم الجديد، ثم ننقل البيانات والأسرار ونختبر الخدمة.

> مثال: يبقى `https://iptv.example.com` ثابتًا داخل التطبيق، بينما يتغير عنوان الخادم خلف DNS من `203.0.113.10` إلى `198.51.100.20`.

## البنية الصحيحة

| العنصر | مكانه | هل يتغير عند تبديل VPS؟ |
|---|---|---:|
| النطاق `iptv.example.com` | شركة التسجيل وDNS | لا |
| عنوان IP | مزود VPS | نعم |
| Caddy وشهادة HTTPS | VPS الحالي | يعاد إصدارها تلقائيًا |
| MongoDB وRedis | VPS الحالي أو خدمة مستقلة | تُنقل البيانات أو تُستعاد |
| APK العميل | GitHub Release/هاتف العميل | لا، إذا بقي النطاق وعقد API ثابتين |
| أسرار الإنتاج | مدير أسرار أو ملف محمي خارج Git | تُنقل بأمان وتُدوّر عند الحاجة |

## الإعداد الموصى به

يُضبط النطاق في ملف الإنتاج كما يلي:

```env
DOMAIN=iptv.example.com
APP_URL=https://iptv.example.com
PUBLIC_BASE_URL=https://iptv.example.com
ALLOWED_ORIGINS=https://iptv.example.com
SUBSCRIPTION_REQUIRED=true
```

وتوجد في المشروع طبقة Caddy تستقبل HTTPS على المنفذين 80 و443 وتوجه `/api/*` و`/health` إلى Backend، بينما توجه بقية الطلبات إلى Frontend. عند وصول النطاق إلى VPS، يتولى Caddy إصدار شهادة Let's Encrypt وتجديدها تلقائيًا.

## خطوات الانتقال بين VPS

قبل الانتقال، نخفض TTL لسجل DNS إلى قيمة قصيرة، ثم ننفذ نسخة احتياطية متحققة من MongoDB وRedis ونحفظ صور Docker والإصدار وأسرار الإنتاج خارج Git. على الخادم الجديد ننسخ ملف البيئة المحمي، نستعيد البيانات، نشغل Compose، ننتظر healthchecks، ثم نختبر `/health` وتسجيل الدخول والتفعيل والتشغيل.

بعد نجاح الاختبارات، نغيّر سجل `A` للنطاق إلى IP الخادم الجديد. يبقى الخادم القديم يعمل مؤقتًا أثناء انتشار DNS، ثم نراقب الطلبات والأخطاء ونوقفه بعد التأكد من أن جميع المستخدمين يصلون إلى الخادم الجديد. لا نغير عنوان API داخل Android طالما بقي النطاق نفسه.

## متى نحتاج إلى إصدار APK جديد؟

لا نحتاج APK جديدًا عند تغيير IP أو مزود VPS فقط. نحتاج إصدارًا جديدًا إذا تغيّر النطاق نفسه، أو تغيّر عقد API، أو تغيّر إعداد Firebase، أو احتاج التطبيق إلى ميزة عميل جديدة. لهذا السبب يجب تثبيت النطاق قبل إخراج APK Release التجاري.

## خيارات الاستضافة

| الخيار | المزايا | العيوب | الملاءمة |
|---|---|---|---|
| VPS مع DNS وCaddy | قابل للنقل، HTTPS تلقائي، يعمل مع Docker الحالي | يحتاج إعداد VPS ونسخ احتياطي | الخيار الموصى به |
| VPS خلف Cloudflare | إخفاء IP، DNS سريع، حماية إضافية | يحتاج ضبط SSL وWebSocket وIP الحقيقي | مناسب بعد استقرار النسخة |
| تشغيل مؤقت داخل بيئة التطوير | سريع للفحص ومشاركة الرابط | الرابط مؤقت، لا ضمان للاستمرارية، لا يصلح للعملاء | اختبار فقط |

## قواعد مهمة

لا نضع IP داخل APK Release، ولا نضع أسرار IPTV أو MongoDB أو Redis داخل Android، ولا نربط العميل بعنوان `localhost` أو `example.invalid`. يجب أن يكون المصدر المرخّص داخل لوحة الإدارة، وأن تبقى روابط المصدر داخل الخادم فقط.
