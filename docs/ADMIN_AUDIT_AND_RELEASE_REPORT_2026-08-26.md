# تقرير تدقيق وتحسين لوحة إدارة DZ HOOF

**التاريخ:** 26 أغسطس 2026  
**النطاق:** لوحة الإدارة، API الخلفية، وظائف مصادر Xtream، قابلية المراقبة، ومسار النشر إلى VPS.  
**الحالة:** الإصدار منشور ومتحقق منه على الإنتاج.

## الملخص التنفيذي

أظهر التدقيق أن لوحة الإدارة ليست مجرد واجهة شكلية؛ معظم صفحات الإدارة الأساسية كانت مرتبطة بمسارات API حقيقية، بما في ذلك القنوات والمستخدمون والخطط والأكواد وEPG والجدولة ومصادر M3U. لكن صفحة **مصادر Xtream** كانت تعرض جزءاً صغيراً من قدرات الخلفية المتاحة، ما جعل أدوات تشغيلية مهمة تبدو مفقودة للمشغّل.

تم تنفيذ تحسين مركز وآمن يربط الواجهة مباشرة بعمليات الخلفية الموجودة مسبقاً: التشخيص الحي، معاينة تغييرات المزامنة قبل تطبيقها، الاسترجاع من آخر snapshot مطبق، وقراءة ملخص صحة المصدر. لم تتم إضافة أي التفاف على قيود مزوّد البث، ولم تُحذف بيانات القنوات أو المستخدمين أو المصادر أثناء العملية.

> النتيجة التشغيلية: تم نشر commit `67eec97dd76e0d97eb4cf7863383cddc60b78ad2` بنجاح، وأعاد فحص الإنتاج `/health` الحالة `ok`، مع بقاء MongoDB وRedis وAPI وFrontend وScheduler في حالة تشغيل سليمة.

## نتائج المطابقة بين الواجهة والخلفية

| المجال | حالة الواجهة قبل التحسين | حالة API | الإجراء المتخذ |
|---|---|---|---|
| مصادر Xtream | قائمة، إضافة، اختبار اتصال، مزامنة، Direct Playback، حذف | أوسع بكثير: diagnostics، preview، snapshots، rollback، catalog import، failover maps، health، watchdog | تم كشف diagnostics وpreview وrollback وhealth في الواجهة |
| مصادر M3U | تدعم preview وsnapshots وrollback وsync واختبار المصدر | متوافقة بدرجة جيدة | استُخدمت كنمط UX مرجعي |
| EPG | status، المصادر، الاختبار، التفعيل والتعطيل، unmatched channels، تعيين tvg-id | متوافق تقريباً مع كامل العقد | لا تغيير تخميني؛ بقيت المعالجة اليدوية مرئية |
| Scheduler | المهام، التشغيل اليدوي، pause/resume، سجل التشغيل | يوجد أيضاً تفصيل run منفصل | سُجلت كفجوة تحسين لاحقة، وليست جزءاً من الإصدار الحالي |
| الإحصائيات | مرتبطة بواجهات stats وstream health | تحتوي مؤشرات تشغيلية متعددة | لم تُستبدل البيانات الحقيقية بمؤشرات تجميلية |

## التحسينات المنفذة

### 1. تشخيص Xtream حي

أضيف زر **تشخيص حي** يستدعي `POST /admin/xtream-sources/:id/diagnostics` مع عينة محدودة. وتعرض الصفحة نتيجة واضحة تفرق بين سلامة API وعدد عينات البث الحي التي استجابت فعلياً. هذا يمنع الخلط بين نجاح تسجيل الدخول إلى لوحة Xtream وبين نجاح التشغيل الحقيقي للقناة.

### 2. معاينة قبل المزامنة

أضيف زر **معاينة التغييرات** يستدعي `POST /admin/xtream-sources/:id/preview` ويعرض أعداد الإضافات والتغييرات والحذف والعناصر غير المتغيرة قبل بدء المزامنة. بذلك تصبح عملية المزامنة قابلة للمراجعة بدلاً من كونها إجراءً أعمى.

### 3. استرجاع آمن

أضيف زر **استرجاع** يقرأ snapshots من `GET /admin/xtream-sources/:id/snapshots` ثم يختار آخر snapshot بحالة `applied` فقط، مع طلب تأكيد صريح قبل تنفيذ `POST /admin/xtream-sources/:id/rollback/:snapshotId`. لا يتم تنفيذ استرجاع عشوائي ولا حذف جماعي غير قابل للعكس.

### 4. ملخص صحة المصدر

أضيف زر **الصحة** الذي يعرض نتيجة `GET /admin/xtream-sources/:id/health`، بما في ذلك عدد القنوات الحية والمتوقفة وعدد مسارات failover المفعلة. كما أضيفت شارة مستقلة لحالة التحقق: `موثّق للتشغيل` أو `بحاجة إلى تشخيص` أو `محجوب`.

## قرارات السلامة وعدم التخريب

احتفظت عملية النشر بمسارها الذري الموجود في المشروع. قبل التفعيل، تم اجتياز بوابة صحة API العامة، وإنشاء وسم rollback للصور، وإنشاء نسخة مصدر كاملة. بعد التبديل، أعيد بناء صور API وFrontend فقط، بينما بقيت خدمات Caddy وMongoDB وRedis دون إعادة إنشاء.

لم يتم تعديل قاعدة البيانات مباشرة، ولم يتم حذف مصادر أو قنوات أو حسابات، ولم تُعرض بيانات اعتماد Xtream في الواجهة أو السجلات. بيانات الاعتماد بقيت مشفرة في الخلفية وفق العقد الموجود في `admin-xtream-sources.js`.

## ملاحظات IPTV التشغيلية

يبقى الفرق بين **مصدر موثّق من ناحية API** و**قناة قابلة للتشغيل الحي** مهماً في بيئة IPTV. قد تنجح metadata أو بيانات الحساب بينما يرفض مزود الخدمة M3U أو البث الحي بسبب صلاحيات الحساب أو عنوان IP أو حد الاتصالات. لذلك أصبحت الواجهة تعرض حالة التحقق والتشخيص بدلاً من اعتبار وجود آلاف القنوات دليلاً على أن القنوات تعمل فعلياً.

لا يحاول هذا الإصدار تجاوز قيود المزوّد أو إعادة توزيع محتوى غير مصرح به. تشغيل Direct Playback أو تفعيل مصدر يجب أن يستند إلى تصريح ومصدر قانوني قابل للتشغيل من VPS الإنتاجي.

## التحسينات التالية المقترحة

الخطوة التالية ذات أعلى قيمة تشغيلية هي إضافة شاشة إدارة failover maps إلى صفحة Xtream، مع استكمال عرض catalog-only import وتشغيل watchdog اليدوي من واجهة الإدارة. كما ينبغي لاحقاً ربط صفحة Scheduler بمسار تفاصيل التشغيل المفرد `GET /scheduler/runs/:id`، وإضافة اختبار تكاملي يثبت أن مؤشرات **Active Channels** و**Stream Health** تستخدمان تعريفاً موحداً للقناة العاملة.

## ملحق الجولة الثانية

بعد طلب استكمال التحسين، أضيفت إلى صفحة Xtream الأدوات التشغيلية المتبقية التالية:

| الأداة | ما تنفذه الواجهة |
|---|---|
| Failover يدوي | إنشاء مسار احتياطي مع `channelRef` و`backupStreamId` واسم البث، ثم عرضه وحذفه بأمان |
| المطابقة الآلية | استدعاء المطابقة الآلية بحد أقصى 500 مسار، مع عرض النتيجة للمشغّل |
| استيراد الكتالوج | استيراد metadata دون تجاوز بوابة التحقق أو تفعيل تشغيل غير موثق |
| Watchdog | تشغيل الفحص الإداري للمصادر من داخل اللوحة وعرض عدد المصادر المعالجة |

تم اجتياز TypeScript وESLint وNext production build بعد هذه الإضافات، ثم دُمجت الجولة عبر [Pull Request #62](https://github.com/mostafabonnif-beep/dzhoot/pull/62). نُشر commit `78e144b45c07ae81f40d248c36a5868fe64a5bac` إلى VPS باستخدام staging وdry-run ثم atomic deploy. بقيت الخدمات الأساسية سليمة، وأعاد `/health` العام `status: ok`، كما لم يظهر OOM في فحص Scheduler.

تظل قاعدة IPTV التشغيلية مطبقة: لا تُنشأ مسارات failover إلا لمصدر احتياطي مصرح به، ولا يعني نجاح استيراد الكتالوج أن البث الحي صالح للعملاء. الواجهة تعرض هذه الحالات منفصلة لتجنب اتخاذ قرار تشغيل خاطئ.
