# نقل DZ HOOF بين Oracle وAWS دون إعادة إنتاج التطبيق

## الإجابة المختصرة

لا، لا تحتاج إلى إعادة إنتاج تطبيق Android أو Frontend عند الانتقال من Oracle إلى AWS إذا بقيت واجهة الـAPI العامة والعقود البرمجية ثابتة. المطلوب هو نشر نفس صور Docker، نقل قاعدة البيانات والملفات والأسرار، تغيير DNS، ثم اختبار الخادم. قد تحتاج إلى إعادة بناء التطبيق فقط إذا تغيّر عنوان API المضمّن داخل APK، أو تغيّر عقد API، أو احتاجت نسخة Android إلى إعداد Firebase/Release جديد.

## مبدأ البنية المحمولة

يُعامل Oracle وAWS كمضيفين فقط. يبقى التطبيق داخل صور Docker، ويُحفظ الإعداد في ملف بيئة إنتاج خارج Git، وتُحفظ MongoDB وRedis في volumes أو خدمات مدارة، بينما يبقى النطاق هو نقطة الدخول الثابتة. لذلك يجب أن يشير التطبيق إلى نطاق مثل `https://iptv.example.com` بدل عنوان IP أو اسم Oracle.

| المكوّن | ما يجب أن يبقى ثابتًا | ما يتغير عند النقل |
|---|---|---|
| Android | نطاق API العام وعقد API | لا شيء إذا بقي النطاق ثابتًا |
| Frontend | صورة Docker وإعداد API النسبي | DNS أو عنوان الخادم خلف النطاق |
| Backend | صورة Docker ومتغيرات البيئة | أسرار وموارد الخادم فقط |
| MongoDB | نسخة احتياطية واسم قاعدة البيانات | مكان volume أو خدمة MongoDB |
| Redis | إعدادات cache/session | volume أو خدمة Redis |
| Caddy | النطاق وACME email | IP وفتح المنافذ 80/443 |
| GitHub Actions | بناء الصور والاختبارات | أسرار registry أو SSH للنشر |

## ما يجب فعله عند النقل

أولًا، خفّض DNS TTL قبل النقل بمدة مناسبة. ثانيًا، خذ نسخة MongoDB احتياطية واختبر الأرشيف. ثالثًا، جهّز الآلة الجديدة وDocker وCompose والجدار الناري. رابعًا، انسخ ملف `.env.production` عبر قناة آمنة ولا ترفعه إلى Git. خامسًا، اسحب نفس `DOCKER_IMAGE` و`DOCKER_FRONTEND_IMAGE` من GitHub Container Registry وشغّل `docker compose -f docker-compose.production.yml up -d`.

بعد تشغيل الخدمات، يجب فحص `/health` و`/ready` وتسجيل دخول المشرف وتجربة كود تجريبي وتشغيل قناة وVOD. بعدها استعد قاعدة البيانات في الآلة الجديدة، اختبر الاشتراكات والأجهزة، ثم غيّر DNS إلى الخادم الجديد. أبقِ الخادم القديم متاحًا لفترة رجوع قصيرة قبل إيقافه.

## متى نحتاج APK جديدًا؟

لا نحتاج APK جديدًا عندما يبقى نطاق API ثابتًا ويتم نقل النطاق عبر DNS. نحتاج APK جديدًا إذا كان التطبيق يحتوي على عنوان IP أو رابط Oracle ثابت، أو تغيرت صيغة API، أو تغيرت إعدادات Firebase، أو أردنا إصدار Release جديد. لهذا السبب يجب إنتاج APK مستقبلي باستخدام نطاق ثابت، لا باستخدام رابط VPS مؤقت.

## فصل الأسرار والبيانات

لا تُنقل الأسرار داخل Git. يجب تخزينها في مدير أسرار أو ملف mode 0600، وتدوير مفاتيح JWT وPlayback وXtream عند الحاجة. لا تُنقل MongoDB وRedis عبر نسخ volumes الخام بين مزودين دون اختبار؛ الأفضل استخدام `mongodump`/`mongorestore` ونسخ Redis عند الحاجة، مع تنفيذ Restore Drill على بيئة اختبار.

## استراتيجية تقليل التوقف

يمكن تشغيل الخادم الجديد بالتوازي على نطاق فرعي مثل `staging.iptv.example.com`، ثم تنفيذ smoke tests. بعد نجاحها، يُحوّل النطاق الأساسي إلى IP الجديد. إذا حدثت مشكلة، يُعاد DNS إلى الخادم القديم، وتُراجع سجلات Caddy وBackend وMongoDB وRedis قبل إعادة المحاولة.

## معيار نجاح النقل

يُعد النقل ناجحًا عندما تعمل healthchecks، وتظهر الخطط والأكواد والمحتوى، ويُقبل كود جديد، ويُرفض الكود المستعمل، ويعمل Live وVOD، ولا تظهر روابط upstream، وتستمر الجلسات وفق السياسة المختارة، وتنجح عملية backup وrestore، ويعمل HTTPS دون تحذير شهادة.

## ملاحظة تشغيلية

Oracle وAWS ليسا جزءًا من منطق التطبيق. أي تكامل خاص بمزود، مثل AWS S3 أو CloudFront أو Oracle Object Storage، يجب وضعه خلف abstraction أو متغيرات بيئة حتى يبقى الانتقال ممكنًا. لا ينبغي ربط كود العميل بخدمة تخزين أو عنوان داخلي لمزود واحد.
