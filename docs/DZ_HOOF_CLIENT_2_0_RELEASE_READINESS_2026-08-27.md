# DZ HOOF Client 2.0 — جاهزية Release

**التاريخ:** 2026-08-27  
**الفرع:** `manus/observability-foundation`  
**الحالة:** غير مفعّل للإنتاج

## الفحص

تم تشغيل مهمة `:app:assembleOfficialRelease` مع رابط Backend الإنتاجي عبر HTTPS. نجحت مراحل التجميع والتحويل حتى خطوة تغليف APK، ثم أوقفها Android Gradle Plugin لأن SigningConfig باسم `release` لا يملك `storeFile` في بيئة الجلسة الحالية.

هذا توقف آمن ومقصود؛ فلا يجوز استخدام APK debug أو إنشاء مفتاح جديد عشوائياً، لأن أجهزة المستخدمين الموجودة يجب أن تستقبل تحديثاً موقّعاً بالشهادة نفسها المستخدمة في النسخ المنشورة سابقاً.

## الحالة الحالية

| العنصر | النتيجة |
|---|---|
| مصدر الإصدار الافتراضي | `1.0.18` / `10018` |
| flavor المطلوب | `official` |
| Backend URL | HTTPS؛ لم يُغيّر |
| Release compilation | وصل إلى التغليف قبل فشل التوقيع |
| سبب الفشل | متغير `SIGNING_KEY_STORE` وملف keystore غير متاحين في الجلسة |
| APK debug للمراجعة | موجود داخلياً فقط، غير صالح كتحديث إنتاجي |
| VPS / `/downloads` / `AppVersion` | لم تُمس |

## تحصين Workflow الإصدار

تم تعديل Workflow الإصدار ليبني `:app:assembleOfficialRelease` فقط، بدلاً من مهمة عامة قد تنتج flavors إضافية. كما أصبح يتحقق من أن versionName يبدأ بصيغة major.minor.patch وأن versionCode المحسوب أكبر من الإصدار المنشور `10017`. تحقق محلياً من أمثلة `1.0.17` و`1.0.18` و`1.0.18-rc.1` دون كشف أي أسرار.

## شرط الإصدار التالي

لتوليد Release صالح، يجب تشغيل البناء في بيئة CI أو جلسة تحتوي ملف keystore الإنتاجي والمتغيرات الأربعة المرتبطة به: مسار الملف، كلمة مرور المتجر، alias، وكلمة مرور المفتاح. يجب عدم تسجيل القيم في السجل أو إرسالها في المحادثة.

بعد توفر البيئة الصحيحة، يلزم التحقق من `applicationId` و`versionName` و`versionCode` وشهادة التوقيع وSHA-256، ثم اختبار تثبيت التحديث فوق نسخة أقدم على جهاز فعلي قبل تسجيل الإصدار في Endpoint التحديث.
