# نسخ قاعدة بيانات DZ HOOT واستعادتها

يوفر المشروع السكربت `server/scripts/backup.sh` لإنشاء نسخة احتياطية مضغوطة من MongoDB بصيغة archive واحدة. يعتمد السكربت على `mongodump`، ولا يطبع قيمة `MONGODB_URI` لأن هذه القيمة قد تحتوي على بيانات دخول.

> **قاعدة تشغيلية:** النسخة الموجودة على نفس الخادم ليست خطة تعافٍ كاملة. يجب نسخ الملفات الناتجة إلى مساحة تخزين منفصلة ومشفرة، واختبار الاستعادة دورياً على قاعدة بيانات غير إنتاجية.

## المتطلبات

يجب تثبيت **MongoDB Database Tools** بحيث يكون الأمر `mongodump` متاحاً، ويجب توفير متغير `MONGODB_URI`. في بيئة Docker يمكن تشغيل الأداة من حاوية أدوات MongoDB أو من المضيف، مع التأكد من أن اسم المضيف في URI قابل للوصول من مكان التنفيذ.

| المتغير | القيمة الافتراضية | الغرض |
| --- | --- | --- |
| `MONGODB_URI` | لا توجد قيمة افتراضية | URI الخاص بقاعدة البيانات؛ لا تضعه في Git أو في سجل الأوامر |
| `BACKUP_DIR` | `/var/backups/dzhoot/mongodb` | مجلد النسخ الاحتياطية |
| `RETENTION_DAYS` | `14` | عدد الأيام قبل حذف النسخ المحلية القديمة |
| `MONGODUMP_BIN` | `mongodump` | مسار بديل لأداة `mongodump` عند الحاجة |
| `ALERT_WEBHOOK_URL` | غير مضبوط | webhook اختياري لتنبيه فشل النسخ؛ لا يُرسل شيء عند تركه فارغاً |
| `ALERT_WEBHOOK_COOLDOWN_MS` | `900000` | مدة منع تكرار تنبيه scheduler لنفس الحدث |
| `ALLOW_RESTORE_DRILL` | `false` | opt-in إلزامي لتشغيل سكربت restore drill |
| `MONGODB_RESTORE_URI` | لا توجد قيمة افتراضية | URI لقاعدة اختبار منفصلة عن الإنتاج |
| `RESTORE_DROP` | `false` | يضيف `--drop` فقط عند تشغيل اختبار قاعدة مخصصة قابلة لإعادة البناء |

## تشغيل نسخة يدوية

من جذر المستودع، شغّل السكربت عبر بيئة لا تسجل الأسرار في history. المثال التالي يمرر URI من متغير بيئي موجود مسبقاً:

```bash
cd /path/to/dzhoot
BACKUP_DIR=/var/backups/dzhoot/mongodb \
RETENTION_DAYS=14 \
MONGODB_URI="$MONGODB_URI" \
  ./server/scripts/backup.sh
```

ينشئ السكربت ملفاً مثل `dzhoot-mongodb-20260812T030000Z.archive.gz`، ويستخدم ملفاً مؤقتاً ثم نقلاً ذرياً حتى لا تعتبر نسخة غير مكتملة نسخة صالحة. كما يطبق صلاحيات `0600`، ويتحقق من سلامة gzip، ويحذف الملفات المطابقة لسياسة الاحتفاظ.

## جدولة النسخ

يمكن استخدام مؤقت النظام أو مهمة تشغيل موثوقة على خادم التطبيق. المثال التالي يشغل النسخ يومياً عند الساعة 03:15، مع تحميل المتغيرات من ملف محمي خارج المستودع:

```cron
15 3 * * * . /etc/dzhoot/backup.env && /opt/dzhoot/server/scripts/backup.sh >> /var/log/dzhoot-backup.log 2>&1
```

يجب أن تكون صلاحيات `/etc/dzhoot/backup.env` مساوية لـ `0600`، وأن يكون مالكها هو حساب الخدمة. لا تضع URI في crontab نفسه، ولا ترسل الناتج إلى سجل عام أو خدمة غير مشفرة.

## نسخ الملفات إلى تخزين منفصل

بعد إنشاء النسخة، انسخها إلى تخزين منفصل باستخدام قناة مشفرة أو أداة تخزين مؤسسية. يجب الاحتفاظ بسياسة متعددة الطبقات، مثل نسخ يومية قصيرة الأجل ونسخ أسبوعية أطول أجلاً، مع تفعيل versioning وMFA أو قفل الحذف عندما يدعم مزود التخزين ذلك. لا يضم السكربت رفعاً تلقائياً إلى مزود محدد حتى لا يفرض على مالك النشر بيانات اعتماد أو بنية تخزين بعينها.

## اختبار سلامة النسخة

يمكن فحص gzip دون استعادة:

```bash
gzip -t /var/backups/dzhoot/mongodb/dzhoot-mongodb-YYYYMMDDTHHMMSSZ.archive.gz
```

هذا الاختبار لا يثبت أن MongoDB ستقبل المحتوى منطقياً؛ لذلك يجب إجراء استعادة تجريبية دورية في بيئة منفصلة.

## الاستعادة في بيئة اختبار

أوقف الكتابة إلى قاعدة الاختبار أو استخدم اسماً مختلفاً لقاعدة البيانات. يوفر المشروع سكربتاً محمياً باسم `server/scripts/restore-drill.sh`، ولا يعمل إلا عند ضبط `ALLOW_RESTORE_DRILL=true`، ويرفض الاستعادة إذا كان URI الاختبار مطابقاً لـ `MONGODB_URI`:

```bash
ALLOW_RESTORE_DRILL=true \
BACKUP_FILE=/var/backups/dzhoot/mongodb/dzhoot-mongodb-YYYYMMDDTHHMMSSZ.archive.gz \
MONGODB_RESTORE_URI="$MONGODB_RESTORE_URI" \
  ./server/scripts/restore-drill.sh
```

إذا احتجت إلى جعل الاختبار قابلاً لإعادة التشغيل فوق قاعدة اختبار مخصصة، أضف `RESTORE_DROP=true` بعد التأكد من أن URI لا يشير إلى الإنتاج. يمكن أيضاً ضبط `MONGORESTORE_BIN` عند استخدام أدوات MongoDB من مسار غير قياسي.

أو استخدم `mongorestore` من إصدار متوافق مع الخادم:

```bash
mongorestore \
  --uri="$MONGODB_RESTORE_URI" \
  --archive=/var/backups/dzhoot/mongodb/dzhoot-mongodb-YYYYMMDDTHHMMSSZ.archive.gz \
  --gzip
```

لا تستخدم `--drop` في الإنتاج إلا بعد موافقة صريحة وخطة رجوع؛ فهو يحذف المجموعات الموجودة قبل الاستعادة. إذا كانت الاستعادة إلى قاعدة باسم مختلف، استخدم `--nsFrom` و`--nsTo` بعد اختبار التحويل على نسخة غير إنتاجية.

## استعادة إنتاجية طارئة

قبل الاستعادة الإنتاجية، يجب إيقاف API والـ scheduler لمنع الكتابة المتزامنة، وأخذ نسخة أخيرة من الحالة الحالية، والتحقق من الملف والـ checksum، ثم تنفيذ الاستعادة ومراجعة الفهارس وتشغيل `/health/ready` و`/health?details=true`. بعد عودة الخدمة، راجع حالة مزامنة Xtream وM3U وEPG، واختبر تسجيل الدخول والتشغيل قبل إعادة فتح الحركة للمستخدمين.

## Restore drill قبل الإطلاق

نفّذ هذا الاختبار في بيئة منفصلة قبل استقبال العملاء، وسجّل التاريخ والنتيجة والمدة:

| الخطوة | دليل النجاح |
| --- | --- |
| إنشاء backup من MongoDB اختبارية | ملف نهائي بصلاحية `0600` و`gzip -t` ناجح |
| نسخ الملف إلى مساحة تخزين منفصلة | الملف موجود خارج خادم التطبيق مع checksum محفوظ |
| استعادة الملف بواسطة `mongorestore` إلى قاعدة اختبار جديدة | الأمر ينجح دون `--drop` على الإنتاج |
| فحص عدد المستخدمين والقنوات والمصادر والبرامج | العدادات منطقية ومطابقة لعينة موثقة قبل النسخ |
| تشغيل API وscheduler في بيئة الاختبار | `/health/ready` يعود سليماً ولا توجد مهام عالقة في `running` |
| تجربة تسجيل الدخول والكتالوج والتشغيل | القناة وVOD يعملان، مع تجديد token عند انتهاءه |
| توثيق RTO/RPO | مدة الاستعادة وفقد البيانات المتوقعان معروفان للمشغل |

## مؤشرات نجاح عملية النسخ

تُعد العملية ناجحة فقط عندما يكون أمر `mongodump` قد انتهى دون خطأ، واجتاز الملف اختبار gzip، وتم نقل الملف من الامتداد المؤقت إلى اسمه النهائي، ثم نُسخ إلى موقع منفصل. يجب مراقبة فشل المهمة وإرسال تنبيه تشغيلي؛ لا تعتمد على وجود المجلد وحده كدليل على نجاح النسخ. عند ضبط `ALERT_WEBHOOK_URL`، يرسل السكربت تنبيهاً عاماً لا يحتوي على URI أو اسم ملف جزئي عند الفشل.
