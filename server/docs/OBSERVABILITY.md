# المراقبة التشغيلية في DZ HOOT

هذا الدليل يحدد ما يحتاجه المشغل لمعرفة حالة النظام قبل أن يكتشف العميل المشكلة. جميع نقاط المراقبة مصممة بحيث لا تعرض كلمات مرور Xtream أو روابط المصدر الأصلية.

## نقاط الفحص

| المسار | الاستخدام | اعتماد MongoDB | رمز النجاح |
| --- | --- | --- | --- |
| `/health/live` | فحص أن عملية Node ما زالت تعمل | لا | `200` دائماً إذا كانت العملية تستجيب |
| `/health/ready` | فحص جاهزية API لقبول الحركة | نعم | `200` عند اتصال MongoDB، و`503` عند الانفصال |
| `/health` | حالة مختصرة للإصدار وMongoDB وRedis | لا للحالة الأساسية | `200` أو `503` حسب MongoDB |
| `/health?details=true` | تفاصيل المصادر وEPG والمهام المجدولة والتنبيه | نعم | يحتوي على بيانات تشغيلية منقحة |

يمكن استخدام `/health/live` مع Kubernetes أو reverse proxy كـ liveness probe، واستخدام `/health/ready` لمنع إرسال الحركة إلى نسخة API لا تستطيع الوصول إلى MongoDB. Redis اختياري في المشروع، لذلك لا يجعل غيابه readiness يفشل وحده.

## Correlation ID

كل طلب يحصل على `X-Request-ID` إذا لم يرسل العميل قيمة صالحة، أو يحتفظ بالقيمة الصالحة القادمة من طبقة موثوقة. يظهر المعرف في سجل Morgan وفي سجلات الأخطاء، ويعاد في الاستجابة. عند استقبال بلاغ من عميل، يجب طلب الوقت التقريبي و`X-Request-ID` إن ظهر في أدوات الشبكة؛ هذا يقلل وقت البحث دون طلب بيانات اعتماد.

## التنبيهات الاختيارية

عند ضبط `ALERT_WEBHOOK_URL`، يرسل backend إشعاراً عند فشل مهمة scheduler أو اكتمالها مع subtask فاشل. يرسل `server/scripts/backup.sh` و`server/scripts/restore-drill.sh` إشعاراً عاماً عند الفشل أيضاً. لا يُرسل النظام العنوان أو URI أو كلمة المرور، ويطبق `ALERT_WEBHOOK_COOLDOWN_MS` لمنع إغراق قناة التنبيه بنفس الحدث.

شكل الرسالة التقريبي هو:

```json
{
  "event": "scheduler:m3u-sync:partial-failure",
  "severity": "warning",
  "message": "M3U Playlist Synchronization completed with 1 failed subtask(s)",
  "details": { "taskName": "m3u-sync", "failedSubtasks": ["m3u:licensed-source"] },
  "sentAt": "2026-08-12T04:00:00.000Z",
  "service": "dzhoot-backend"
}
```

يجب استخدام عنوان HTTPS مملوك للمشغل، وعدم وضع webhook في Git أو في رسائل الخطأ. ترك المتغير فارغاً يعطل الإرسال دون تعطيل المزامنة أو النسخ.

## مؤشرات يجب متابعتها في Beta

قبل الإطلاق الواسع، راقب زمن بدء التشغيل، نسبة إعادة المحاولة، نسبة الانتقال إلى alternate، أخطاء `401/403` في authorization، فشل مزامنة Xtream/M3U، عمر آخر EPG ناجح، وحجم قاعدة البيانات. لا يكفي أن يكون `/health` أخضر؛ يجب مقارنة هذه المؤشرات مع تجربة مستخدم حقيقية على أجهزة TV.

## حدود التحقق الحالي

تم اختبار notifier وbackup وrestore-drill محلياً بأدوات وهمية آمنة، ونجحت فحوص syntax وgzip والصلاحيات ومنع URI الإنتاج. لم تُنفذ استعادة MongoDB فعلية في هذه البيئة لأن `mongorestore` غير مثبت ولا توجد قاعدة اختبار متصلة. يجب تنفيذ restore drill حقيقي قبل الإطلاق، وتسجيل RTO/RPO والعدادات بعد الاستعادة.
