# Device Token Migration

## الهدف

الانتقال من `channelListCode` قصير وقابل للمشاركة إلى **device access token** عشوائي مرتبط بجهاز واحد. هذه الخطة لا تتضمن نشر production أو تعديل أسرار؛ هي دليل للمشغّل بعد مراجعة طلب التغيير والموافقة عليه.

## حالات العميل

| العميل | المسار المستهدف | ملاحظة |
|---|---|---|
| Android الرسمي | تفعيل العميل ثم حفظ `deviceAccess.token` وإرسال `X-Device-Token` | المسار المعتمد |
| عميل web/session | يطلب بيانات لا تتطلب URL خام، أو يربط جهازاً لتشغيل المحتوى | لا يصدر `pt1` افتراضياً |
| M3U قديم | نافذة توافق محددة زمنياً فقط | لا يدعم هوية جهاز قوية |
| عميل code قديم | إعادة تفعيل الجهاز | يعيد 410 عندما تكون الراية مغلقة |

## ترتيب النشر المقترح

1. انشر بعد نجاح CI إلى staging فقط، مع `ALLOW_LEGACY_TV_CODE=false` و`ALLOW_LEGACY_PLAYBACK_TOKEN=false`.
2. فعّل جهاز Android جديد وتحقق من أن `POST /tv/playback-token` ينتج `pt2`، وأن التشغيل وHLS nested segments يعملان.
3. تحقق من رفض الرمز المفقود أو المبطل أو المنتهي، ومن أن دوران رمز الجهاز يبطل `pt2` السابق.
4. راقب أخطاء `LEGACY_TV_CODE_DISABLED` و`LEGACY_PLAYBACK_TOKEN_DISABLED` وطلبات 401/403 لمدة متفق عليها.
5. إذا كان يوجد عملاء M3U متعاقد عليهم، أنشئ نافذة توافق قصيرة وموثقة: فعّل الرايتين معاً، أخطر العملاء بتاريخ الانتهاء، وقصر الحسابات المتأثرة. لا تجعل التوافق إعداداً دائماً.
6. أعد القيم إلى `false` بعد ترحيل آخر عميل، ثم راقب رفض `pt1` ومسارات code.

> لا تفعّل `ALLOW_LEGACY_TV_CODE` وحده لتصدير M3U. التصدير القديم يحتاج أيضاً `ALLOW_LEGACY_PLAYBACK_TOKEN=true` لأنه ينتج `pt1`.

## متغيرات البيئة

| المتغير | الحالة النهائية | الاستخدام |
|---|---:|---|
| `ALLOW_LEGACY_TV_CODE` | `false` | يمنع verify/pair/EPG/playlist القائمة على code |
| `ALLOW_LEGACY_PLAYBACK_TOKEN` | `false` | يمنع قبول وإصدار `pt1` |
| `PLAYBACK_TOKEN_SECRET` | سر قوي موجود | تشفير playback tokens |
| `DEVICE_ACCESS_TOKEN_TTL_MS` إن وجد | وفق سياسة المنتج | يحد عمر device token |

لا تحفظ قيمة token الخام في `.env` أو Git أو ملف تذاكر. تحفظ MongoDB hash فقط، وتظهر القيمة مرة واحدة للعميل عند التفعيل أو الدوران.

## اختبار القبول

| اختبار | النتيجة المتوقعة |
|---|---|
| تفعيل جهاز جديد | `deviceAccess.token` موجود، hash فقط مخزن |
| token صالح في `X-Device-Token` | مزامنة وتشغيل مسموحان ضمن الاشتراك |
| token مبطل/مدوّر | 401؛ لا يعمل `pt2` القديم |
| اشتراك منتهٍ أو مستخدم معطل | 403 عند إصدار وتشغيل البث |
| code أو `pt1` مع الرايات `false` | 410 أو رفض التحقق |
| HLS child token | يرث device identity ولا يعمل بجهاز آخر |

## التراجع

التراجع الأول هو rollback للإصدار السابق وفق [RELEASE_RUNBOOK.md](./RELEASE_RUNBOOK.md)، وليس تعطيل ضوابط الأمان فوراً. إذا أثبتت المراقبة أن هناك عميل legacy ضروري، يمكن فتح نافذة توافق مؤقتة بالرايتين معاً، مع مدة انتهاء ومالك مسؤول ومراقبة للطلبات؛ لا تُنشر أسرار ولا تُعاد source URLs.

إذا تعطل التفعيل نفسه، أصلح endpoint أو إصدار العميل أولاً. لا تُستبدل المشكلة بإعادة استخدام channelListCode كاعتماد أساسي.
