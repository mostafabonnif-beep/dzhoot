# حوكمة GitHub المجانية المؤقتة — DZ HOOF

**الحالة:** سارية إلى أن تصبح حماية فروع GitHub متاحة للحساب.
**النطاق:** المستودع الخاص `mostafabonnif-beep/dzhoot` والفرع `main`.

## سبب هذه السياسة

تعذر تفعيل حماية الفرع `main` تقنياً من خلال GitHub في الحالة الحالية، لأن GitHub أعاد رسالة تفيد بأن الحماية لمستودع خاص تتطلب GitHub Pro أو جعل المستودع عاماً. لا ينبغي جعل مشروع DZ HOOF عاماً لمجرد الحصول على هذه الخاصية، لأن الخصوصية تتقدم على هذا البديل. لذلك تنشئ هذه الوثيقة وقالب PR ممارسة تشغيلية إلزامية قابلة للتطبيق مجاناً، لكنها ليست بديلاً تقنياً كاملاً عن الحماية التي تمنع الدفع المباشر إلى `main`.

> **المبدأ:** لا يُدفع إلى `main` مباشرة. كل تغيير، مهما كان صغيراً، يبدأ بفرع مستقل وطلب مراجعة وCI أخضر وتوثيق أثر الإنتاج.

## مسار الدمج الإلزامي

| المرحلة | المسؤول | شرط الإتمام |
|---|---|---|
| إنشاء الفرع | المطور | يبدأ من `origin/main` الحالي ويحمل اسماً يصف المهمة |
| تنفيذ التغيير | المطور | لا أسرار ولا ملفات بيئة ولا روابط بث خامة في Git |
| فتح طلب مراجعة | المطور | يستخدم قالب PR ويملأ قسم الاختبار والأثر وخطة الرجوع |
| التحقق الآلي | CI | نجاح الحماية من الأسرار والـ backend والواجهة وAndroid بحسب نطاق التغيير |
| المراجعة البشرية | مالك أو عضو موثوق | قراءة diff وأثر الإنتاج، خصوصاً بيانات القنوات والأمان والفوترة |
| الدمج | المسؤول المخول | لا يتم إلا بعد CI الأخضر والمراجعة؛ يفضل merge commit لحفظ الأثر |
| النشر | مسؤول التشغيل | نسخة احتياطية متحققة وصحة قبل وبعد النشر وسجل rollback |

## قواعد منع المخاطر

لا يجوز إزالة provenance أو الحقوق أو سجل التدقيق من البيانات لمجرد تنظيف واجهة المشاهد. لا يجوز تغيير قاعدة بيانات الإنتاج أو الأسرار أو firewall أو حسابات العملاء من PR غير مخصص لذلك. ويجب عزل تغييرات البنية أو الهوية أو API أو Android في PRs صغيرة قابلة للرجوع بدلاً من دمج تحسينات كثيرة غير مترابطة دفعة واحدة.

عند الضرورة القصوى لإصلاح إنتاجي، ينشأ `hotfix/` من `main` مع PR مختصر وCI. إذا كان التجاوز ضرورياً لمنع تعطل الخدمة، يوثق السبب ووقت التجاوز وخطة المتابعة في تقرير الحادث، ثم ينفذ PR لاحق يعيد المسار إلى الحالة المراجعة.

## نقطة ترقية لاحقة

عند توفر GitHub Pro للحساب، تُستبدل السياسة اليدوية بقاعدة تقنية تتطلب فحوص `Secret guard` و`backend` و`frontend` و`android`، ومراجعة واحدة على الأقل، وحل جميع المحادثات، ومنع force-push وحذف الفرع. يبقى المستودع خاصاً في جميع الحالات.
