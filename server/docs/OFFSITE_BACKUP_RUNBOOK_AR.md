# دليل النسخ الاحتياطي الخارجي المشفر — DZ HOOF

هذا الدليل يكمل النسخ المحلية الموجودة على VPS ولا يستبدلها. الهدف هو الاحتفاظ بنسخة مشفرة في **مكان مستقل عن VPS** يمكن استخدامها عند فقدان الخادم كاملاً. تعتمد الآلية على Restic، الذي يشفر المحتوى قبل رفعه إلى الوجهة المحددة.

> لا تضع مفاتيح التخزين أو كلمة مرور Restic أو مفتاح SFTP في Git أو ملف `.env.production` أو سجل systemd. تحفظ جميعها تحت `/etc/dzhoot/` بصلاحية `0600` فقط.

## اختيار الوجهة

| الخيار | مناسب عندما | ما يحتاجه |
|---|---|---|
| SFTP على خادم ثانٍ تملكه | لديك خادم أو NAS مستقل عن VPS | مضيف SFTP ومستخدم ومسار تخزين ومفتاح SSH مخصص للنسخ |
| S3 متوافق | لا تملك خادماً ثانياً وتريد مساحة كائنات منفصلة | رابط المستودع ومفتاح وصول ومفتاح سري وإقليم عند الحاجة |

لا تعد النسخة الموجودة على القرص نفسه أو على نفس حساب VPS نسخة خارجية. لا تستخدم حساباً أو خادماً تشارك بيانات دخوله مع الإنتاج كوجهة وحيدة للاستعادة.

## تهيئة آمنة

ينسخ المسؤول النموذج إلى موقع محمي، ثم يضع قيمة واحدة فقط لعنوان Restic المناسب للوجهة. يجب إنشاء ملف كلمة المرور خارج Git؛ لا يكتب في سطر الأوامر ولا يرسل في الدردشة.

```bash
sudo install -d -m 700 /etc/dzhoot
sudo install -m 600 /opt/dzhoot/server/scripts/backup/restic-offsite.env.example /etc/dzhoot/restic-offsite.env
sudo install -m 600 /dev/null /etc/dzhoot/restic-offsite-password
sudoedit /etc/dzhoot/restic-offsite.env
sudoedit /etc/dzhoot/restic-offsite-password
```

عند استخدام SFTP، ينشئ المسؤول مفتاح SSH مخصصاً للنسخ وصلاحياته `0600`، ثم يهيئ العميل وفق إعدادات Restic المعتمدة. عند استخدام S3، تضاف فقط مفاتيح الحساب الذي يملك صلاحية محصورة بحاوية النسخ ولا يملك صلاحيات إدارة عامة.

## التحقق والتفعيل

قبل رفع أي بيانات، ينفذ المسؤول وضع المعاينة. إذا نجح ولم يطبع قيماً حساسة، يمكن تهيئة مستودع Restic مرة واحدة من جلسة root محمية ثم تشغيل نسخة أولية ومراجعة النتيجة.

```bash
sudo /opt/dzhoot/server/scripts/backup/restic-offsite-backup.sh --dry-run
sudo /opt/dzhoot/server/scripts/backup/restic-offsite-backup.sh --init
sudo /opt/dzhoot/server/scripts/backup/restic-offsite-backup.sh --backup
sudo /opt/dzhoot/server/scripts/backup/install-restic-offsite-service.sh
```

يشغل المؤقت نسخة يومية عند 03:20 UTC مع تأخير عشوائي قصير، وفحصاً أسبوعياً لجزء من بيانات المستودع. لا يعد نجاح النسخ دليلاً كافياً على الاستعادة؛ يجب تنفيذ restore drill شهري على قاعدة اختبار منفصلة ثم تسجيل التاريخ والنتيجة.

## الاستعادة التجريبية

تنفذ الاستعادة في بيئة اختبار أو VPS بديل، وليس فوق قاعدة إنتاج نشطة. تستعيد نسخة Restic إلى مجلد مؤقت، ثم تفحص checksum وتستورد أرشيف MongoDB في قاعدة اختبار مختلفة. بعد ذلك يتم اختبار الصحة وتسجيل نتيجة التجربة. دليل المشروع `BACKUP_RESTORE.md` يشرح حماية restore drill من توجيهه إلى MongoDB الإنتاجية.

| فحص القبول | المطلوب |
|---|---|
| استعادة ملفات snapshot | نجاح Restic وظهور أرشيف MongoDB وملف checksum |
| سلامة الأرشيف | نجاح `gzip -t` و`sha256sum -c SHA256SUMS` |
| استيراد قاعدة اختبار | نجاح `mongorestore` إلى قاعدة لا تطابق الإنتاج |
| فحص التطبيق | نجاح health endpoint في البيئة الاختبارية |
| توثيق النتيجة | تاريخ الاختبار واسم snapshot والمدة وأي عائق |

## الاستبقاء والمسؤوليات

يحتفظ السكربت بسبع نسخ يومية وأربع أسبوعية وثلاث شهرية. يجب على مالك المشروع الاحتفاظ بكلمة مرور Restic ومفتاح SFTP أو مفاتيح S3 في مدير كلمات مرور مستقل؛ فقدان كلمة مرور Restic يمنع استعادة النسخ المشفرة. وينبغي تدوير مفاتيح الوصول عند تغيير الفريق أو الاشتباه في كشفها.
